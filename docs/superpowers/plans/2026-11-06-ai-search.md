# AI search ("Ask") Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Editors can ask the catalog plain-language questions at `#/ask` and get a short answer plus a list of real recipes and books, produced by a bounded Claude tool-use loop over the existing read-only MCP tools.

**Architecture:** Two refactors in `extras.py` expose the MCP tool dispatch (`run_tool`) and the Messages API POST (`messages_api`) as shared helpers. A new `ask.py` module owns the `ask_log` table, thread validation, the daily cap, the tool loop and result hydration behind `POST /admin/api/ask` (`@editor_required`). The SPA gains an `#/ask` view that renders hydrated items with the existing `recipeRow()` and book cards.

**Tech Stack:** Python 3.12+, Flask, SQLite, plain `urllib` (no SDK), vanilla JS SPA, pytest, Playwright (optional, skipped when absent).

**Spec:** `docs/superpowers/specs/2026-11-06-ai-search-design.md` — the source of truth. If code contradicts it, stop and ask; don't redesign.

## Global Constraints

- Feature is off unless a key is configured: `ANTHROPIC_SEARCH_KEY`, falling back to `ANTHROPIC_API_KEY`.
- Model default `claude-haiku-5-5` (`ANTHROPIC_SEARCH_MODEL`); `ASK_DAILY_LIMIT` default `200`.
- Limits: 5 rounds per question (5th forces `show_results`), 5 `q` per thread, 60 s per question, 25 s per API call, `max_tokens` 2048.
- Thread: `q` ≤ 500 chars after `clean()` and non-empty; `a` ≤ 1,000 chars; `answer` truncated to 600 chars.
- `show_results`: `recipe_ids` maxItems 25, `book_ids` maxItems 10.
- Write tools (`WRITE_TOOLS`) are never offered to the model. Tools run with `private=True`.
- Schema change is one new table + index (`ask_log`); no existing table, column or row changes. Question text is never stored.
- Plain `urllib`, no new runtime dependency.
- `python -m pytest -q` green after every task.
- Public repo: no personal hostnames, names, emails or home paths in code, docs, tests or commit messages; use `cookbooks.example.com` and `@example.com`. `tests/test_hygiene.py` covers IDs and paths only; check every diff by eye for names and hostnames, plus:
  `git diff --cached -U0 | grep -nEi '[a-z0-9-]+\.(com|net|org|io|dev|app)\b' | grep -vi 'example\.\(com\|org\)\|anthropic\.com\|claude\.com\|github\.com\|openlibrary\.org\|cloudflare'` must print nothing new.
- Conventional commit messages, small commits, one per task.

## Decisions this plan pins (where the spec leaves a choice)

1. **Unknown tool in `run_tool`:** raises `UnknownTool(LookupError)`. `handle_rpc` maps it to JSON-RPC `-32602 "Unknown tool: <name>"` (today's behaviour); Ask turns it into an `is_error` tool result `"Unknown tool: <name>"`.
2. **`messages_api` errors:** only `urllib.error.HTTPError` becomes `ClaudeAPIError(status, detail)`. Timeouts and `URLError` propagate unchanged, so `call_claude()`'s behaviour (and the photo job's error text) is identical; `call_claude` re-raises `ClaudeAPIError` as today's `RuntimeError(f"Claude API error {status}: {detail}")`.
3. **Recipe item fields:** `{"kind": "recipe", **recipe_dict(row, True)}` from `core.recipes_by_id()` — the same fields the editor recipe API returns, so the book name is `book_title` (the spec example's `book` defers to "what the existing recipe API returns to editors"). Book items: `{"kind": "book", **book}` from `core.book_dicts(rows, True)`.
4. **Which ids count as "seen":** walk every tool result: a dict with `id` and `title` → book id; a dict with `id` and `name` and any of `page`/`heading`/`book_id`/`url` → recipe id; any `book_id` integer → book id. (Covers `search_recipes`, `search_books`, `get_book` incl. its nested recipes, `suggest_recipes`, `cooking_stats` `top_books`/`top_recipes`/`never_cooked`; ignores `list_categories` names.)
5. **What gets logged in `ask_log`:** every request that passes the key check and validation (status `ok`, `capped`, `api_error`, `timeout`). 503 (no key) and 400 (bad thread) are not logged — no question was asked. Check order: key → validation → cap.
6. **429/529 retry:** once per API call, after `time.sleep(2)` (monkeypatched in tests).
7. **Round 5 without `show_results`** (shouldn't happen with forced `tool_choice`): respond 200 with any text as `answer` and `items: []`, status `ok`.
8. **UI Playwright test** lives in `tests/test_ask_ui.py`, not `test_ask.py`, because `pytest.importorskip("playwright...")` at module level would otherwise skip the whole API suite where Playwright is missing (CI doesn't install it).
9. **`recipeRow()` in Ask:** it reads `S.bookTitle` / `S.bookPhotos` for the Dinner Log link and photo count. The Ask view sets `S.bookPhotos = []` and sets `S.bookTitle = r.book_title` before rendering each row, so the 🍽 link names the right book.

## Review Focus

1. **Model returns ids as strings or floats** (`"812"`, `812.0`) in `show_results` → coerced like `check_args` does for integers; non-numeric entries dropped, never a 500. Test in Task 4.
2. **Model calls several tools in one response, including `show_results` alongside a search** → other tool_use blocks are ignored and `show_results` is hydrated against ids seen *before* this response; nothing it couldn't have seen appears. Test in Task 4.
3. **Same id listed twice, or a recipe that was deleted between the tool call and hydration** → deduplicated, order kept; missing rows silently skipped. Test in Task 4.
4. **Non-JSON or non-object request body** (`text/plain`, `[]`, `null`) → 400 with a short message, not 500. Test in Task 3.
5. **Answer text containing HTML** (`<img onerror=…>`) → rendered as text in the UI (`esc()`), never `innerHTML` of model text. Covered by the smoke test's stubbed answer containing `<b>` and asserting it shows literally (Task 6).
